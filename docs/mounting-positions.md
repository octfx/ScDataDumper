# Mounting positions dump contract

`MountingPositions` is a top-level list in new ship dumps, including `[]` for a ship with no eligible ports. A missing field means the dump predates this contract. Do not synthesize it from `Systems.WeaponMounts` or the legacy turret lists. The build version is supplied by the snapshot/import, not by each position.

## Position schema

| Field | Type | Meaning |
| --- | --- | --- |
| `PortId` | string | Unique link to a `Loadout` entry in this snapshot. Do not persist as a cross-build ID. |
| `HardpointName` | string, optional | Raw port name. Can repeat. |
| `Occupied` | boolean | The snapshot has a resolved installed item at the port. |
| `MinSize`, `MaxSize` | integer | Port capacity. Zero uses the loadout's existing unknown/default convention. |
| `InstalledSize` | integer, optional | Installed item's declared size, distinct from port capacity and legacy `Size`. |
| `MountType` | enum, optional | `Fixed`, `Gimbal`, `Turret`, `Rack`, `Missile`, `Tool`, or `Device`. Omitted for a vacant position or unknown installed mount type. |
| `TurretRole` | enum, optional | `Manned`, `Remote`, `Pdc`, or `Autonomous`. Omitted for non-turrets or unknown roles. |
| `Payload` | list | Installed payload in loadout traversal order. Every entry includes `PortId` and the known fields from `HardpointName`, `UUID`, `ClassName`, `Name`, `Type`, `Size`. A direct installation can use the row's own ID. Child gun or missile ports are not separate positions. |
| `OperatingStations` | list, optional | Verified places a player can occupy to fire the installed weapon or use the installed tool. Each has `Kind` (`Pilot`, `Crew`, or `InTurret`), snapshot-local `SeatPortId`, and a human station label `Name`. An integrated seat uses the mounting position's own ID. Applies to every mount type. Omission means unknown, not inoperable; a present list need not exhaust all stations. Technical `ControlRoutes` are not exported. |
| `IsPilotSlaveable` | boolean, optional | Existing flag where uniquely attributable. Not evidence of a pilot route. |
| `CombatStats` | object, optional | Existing DPS aggregator projection without `HardpointName`: `Dps`, `SustainedDps`, `Alpha` for weapons and `MissileDamage` for missiles, as applicable per installed item. Actual payload aggregation; may differ from the legacy summary. |
| `LegacyBucket`, `LegacyOrdinal` | string and integer, optional | Legacy bucket and zero-based row order when attribution is unique. Migration inputs, not public API fields. |
| `LegacySize` | integer, optional | Legacy size override when installed size and port capacity cannot recover it. |

The linked loadout entry carries the same optional `MountType` and `TurretRole`. Get the installed assembly's identity and compatible types from that entry. Eligibility needs installed weapon/utility equipment or compatible types. Hull attachments can host independent ports (for example, the Grin MDC rear module PDC); ordinary nested attachment ports and personal weapon lockers are not mounting positions.

**EMP qualifies** as a `Device`; quantum interdiction equipment does not. **The Reclaimer claw qualifies** as a `Tool` and carries its salvage emitter on the arm row. The Prospector mining arm and Starfarer refueling arm are also tools, not turrets.

A locked empty port is not evidence of a usable position. Keep it when its identity matches a legacy summary so attribution can be checked separately. This excludes the Warden's inherited S5 launcher slot while keeping the Harbinger's installed launcher. The base MPUV's inactive arm is not a vacant utility position. The vacant rack and utility integration cases use modified loadouts, not stock configurations.

`MountingPositionIssues`, when present, is a list of diagnostics. Each has `Reason`, optional `HardpointName`, and candidate `PortIds`; legacy identity failures also have `Bucket` and `Ordinal`. `UnresolvedLegacyTurret`, `UnresolvedCombatStats`, `AmbiguousCombatStats`, and `AmbiguousSlaveability` block legacy parity. The old DPS aggregator groups by hardpoint name and may already have merged contributions before export. Do not attribute that result when multiple DPS source ports share the name. A child gimbal that cannot source turret stats is not a candidate. Old summaries, loadout stats, and totals stay unchanged even on a collision.

## Operating station evidence

The resolver joins vehicle script ports to unique installed loadout entries before using their snapshot-local IDs. It accepts active direct seat bindings and exclusive seat tag grants through installed weapon controllers whose tag matches the mount. Numeric priority alone does not grant operation. Salvage payloads also need a matching exclusive `SalvageController` grant at the seat. An integrated turret seat needs an exclusive mount-type use grant plus an exclusive action grant for its installed guns or tractor beam. An integrated mining cab instead needs exclusive access to its tagged installed `MiningController`, which grants exclusive `WeaponMining` use for the cab tag. Explicit user-side denial or ambiguous groups suppress attribution. Numeric user priorities are not action evidence; the exclusive use grant is. The seat component alone is not action evidence. This does not require an external controller route. A direct binding on an empty housing is unresolved. Module aim routes do not establish tool operation.

Default pilot fire needs a nonempty default weapon group, one installed weapon controller with empty default `Turret` and `WeaponGun` groups, and one pilot with an empty default or explicit symbolic `exclusive_control` `WeaponController` group. Two distinct seat routes reach it. The old default-seat route requires mount and controller tags both empty or both matching the pilot's physical seat tag (the 300i and Aurora Mk2 patterns). The exact exclusive-controller claim route instead accepts a recognized pilot holding a single `WeaponController` group that explicitly grants the exact nonempty mount/controller tag `exclusive_control`, with the pilot's physical tag allowed to differ (the Stingray `pilotSeat`/`weaponPilot` pattern); it additionally requires exactly one bound seat port, a stricter restriction than the old route, independently verified against the Stingray's actual sole human station (integrated turret seats are not bound seat ports, so this count is not a whole-ship seat census). Competing default or numeric seat claims suppress both routes. Dedicated bindings, tags, competing controllers, and ambiguous source identities suppress this inference. The 300i, Carrack, Freelancer, and Reclaimer traces cover these mechanisms. With more than one installed weapon controller, a third route covers the Redeemer wing-gun pattern: the gun mount carries a nonempty default weapon group and exactly the recognized pilot's physical seat tag, one differently tagged controller supplies strictly bare-default `Turret` and `WeaponGun` groups, exactly one recognized human pilot seat (player-operable record, seat tag equal to the mount tag) holds that controller tag `exclusive_control`, and no other seat makes any default, numeric, mount-tag or controller-tag `WeaponController` claim. Every other installed weapon controller must be separately scoped: a nonempty distinct tag whose `Turret`/`WeaponGun` groups are strictly well-formed and either flat literal denials or tag-scoped grants that do not cover the mount tag; any bare, numeric or symbolic default, or an untagged extra controller, is a plausible competitor. Autonomous or PDC mounts and unresolved direct bindings suppress this route, and all installed weapon controllers must be bound. Legacy bridge attribution, slaveability, and combat stats do not use the operating station resolver.

Explicit remote gun and missile chains can use different controller and mount tags. The seat must exclusively hold the controller tag; that installed weapon or missile controller must exclusively grant both the installed mount type and the matching payload action (`WeaponGun` or `Missile`) for the mount tag. Require one matching action controller and one exclusive seat holder, with actual installed matching payload. Numeric grants do not qualify for this extension.

Conditional tractor operation needs the complete Hull C pattern: one tagged seat with exclusive weapon and salvage controller access, one matching exclusive turret-aim controller, one installed salvage controller, an actual tractor-beam payload, and a turret item requiring its remote camera. The tool's sole `TractorBeam` condition must be `no_control` to `exclusive_control` under exactly `Condition_And(Condition_Tag, Condition_AllowedByRemoteTurretView)`. Seat, controller, mount and condition tags must agree. Extra conditions, conflicting grants, numeric priorities and ambiguous holders stay unresolved. This reports configured access through the remote view, not unconditional runtime control.

Four narrow tool/device families extend the evidence. They share strict guards: no direct controllers on the mount, no name ambiguity, installed relevant controllers counted before the join (an unbound relevant controller or an unbound top-level seat blocks the rule), strictly well-formed unconditional priority groups (only `itemType`/optional `defaultPriority` attributes, only `tags` nodes containing one childless `Priority` leaf, no duplicate case-insensitive targets), unresolved conditional action treated as a competing claim, resolvable item records behind the selected controller, action root, and installed payload nodes (every payload ancestor record must resolve, not only the payload node), and an actual human seat item record: `SCItemSeatParams` plus an available, enabled, player-usable `OperatorSeatAlignmentSlot`. Tagged rules use whole-tag equality, and any other bound salvage controller holding a numeric, default, conditional, or unknown-shape claim for the needed action competes regardless of its own tag. A competing holder is excluded only when its single well-formed group denies the tag literally; multiple or unknown-shape holder groups always compete. An untagged default EMP route accepts a concrete `EMP` root item with `SCItemEMPParams`, one untagged installed-and-bound weapon controller with a single bare-default `EMP` use group, and one recognized human pilot holding a bare-default or default-exclusive `WeaponController` group; literal observe-only seats do not compete. It does not require a default weapon group (the Sabre Raven pattern) and never covers tagged devices. A tagged exclusive salvage route accepts a `ToolArm` or `SalvageFieldEmitter` root (or any mount with an installed tractor-beam descendant) whose nonempty tag is held by exactly one installed salvage controller with an explicit `exclusive_control` use grant for the exact root action, and exactly one human seat holder with an explicit exclusive `SalvageController` grant for that tag; seats that unambiguously deny the tag do not compete, but numeric or default claims do. An untagged default salvage route accepts only the reviewed root shapes: a `ToolArm` with an installed salvage head (requiring bare-default use for both `ToolArm` and `SalvageHead`) or a `SalvageFieldEmitter` root, one untagged installed-and-bound salvage controller, and a sole recognized human pilot with bare-default or default-exclusive salvage membership; it never infers scope onto tagged mounts or controllers. The tagged exclusive tractor route is the salvage-holder chain with the `TractorBeam` action; numeric weapon-controller aim claims neither grant nor block it.

Default pilot missile operation uses a separate tested pattern: loaded, untagged missile racks, one untagged installed `MissileController` with empty default `MissileLauncher` and `Missile` use groups, and one pilot seat whose single `MissileController` group is an empty default (or explicit default `exclusive_control`) or a strictly flat positive numeric `defaultPriority` (the Redeemer pattern; zero, negative, symbolic-unknown, tag-scoped or malformed groups do not qualify). A competing seat is excluded from the potential-operator set only when its `MissileController` groups number exactly one and that group is a strictly literal default `observe_only` (exactly `itemType` and `defaultPriority`, no tag children); the Shiv copilot pattern. With exactly two competing seats the route additionally accepts the shared claim of one recognized default pilot plus exactly one copilot whose single group is a strictly flat positive numeric `defaultPriority` (the Hammerhead GS/Tiburon pattern); copilot identity is the exact seat type `Seat.Copilot` or an exact case-insensitive seat tag `copilotSeat`/`copilot_seat`, and both seats must resolve to actual player-operable human seat records. Any other claim - numeric or `no_control` defaults, bare defaults, explicit tag grants, unknown attributes, duplicate groups - still blocks the route. Pilot identity is the exact seat type `Seat.Pilot` or an exact case-insensitive seat tag `pilotSeat`/`Pilot_Seat` (the Ares Starfighter pattern, where the installed pilot seat is `Seat.UNDEFINED`). Near-miss tags such as `CoPilot_Seat` or `Pilot_Seat_Other` do not identify a pilot. Missing payloads, dedicated routes, competing seat grants or controllers, and ambiguous identities leave this path unresolved. Missile racks do not need a gun's `defaultWeaponGroup`.

## Reconstructing the legacy API projection

Select positions with `LegacyBucket` and sort within each bucket by `LegacyOrdinal`. Resolve each linked loadout entry by `PortId`. Reconstruct the legacy projection for comparison in tests only; never read the old summary as an input. Keep missing values and empty lists distinct. Do not infer legacy flags from `MountType` or `TurretRole`.

| Legacy API field | Input or rule |
| --- | --- |
| `category` | Decorate from `LegacyBucket` as `manned`, `remote`, or `pdc`. |
| `display_name` | Linked `PartDisplayName` when the key exists, otherwise `PortDisplayName`. An explicit null part label does not fall back to the port. |
| `hardpoint_name`, `part_name` | Linked `HardpointName`, `PartName`. |
| `turret_type`, `class_name` | Linked `Type`, `ClassName`. |
| `size` | `LegacySize` if present, otherwise the first positive linked `InstalledSize`, `MaxSize`, `MinSize`, or zero. |
| `turret`, `gimballed`, `fixed` | Legacy turret bucket rows do not emit these flags. Preserve the resource's defaults. |
| `mount_count` | Number of reconstructed mounts; no count when there are no mounts. |
| `weapon_sizes`, `payload_sizes`, `payload_types`, `payload_class_names` | `WeaponSizes`, `PayloadSizes`, `PayloadTypes`, `PayloadClassNames`; when absent, use the resource's stable, strict unique aggregation across `Mounts`. Do not deduplicate explicit lists. |
| `mounts` | `Mounts`, retaining valid rows and order. Map `display_name` from `DisplayName ?? Name`, `hardpoint_name` from `HardpointName`, `mount_type` from `MountType ?? Type`, `class_name` from `MountClassName ?? ClassName`, `size` from `Size ?? MaxSize ?? MinSize`, and the four payload/weapon lists from their names above without aggregation. |
| `dps_total`, `sustained_dps_total`, `alpha_total`, `is_pilot_slaveable` | `DpsTotal`, `SustainedDpsTotal`, `AlphaTotal`, `IsPilotSlaveable` exactly as exported. |
| `weapons` | `Weapons`, retaining valid rows and order. Map `uuid`, `class_name`, `name`, `dps`, `sustained_dps`, `alpha`, and `is_pilot_slaveable` from `UUID`, `ClassName`, `Name`, `Dps`, `SustainedDps`, `Alpha`, and `IsPilotSlaveable`. Derive `link` and `web_url` from the UUID and API request version; use null without a UUID. |
| `version` | Response metadata for the imported snapshot. |

For the legacy mount fields above, use the linked entry's immediate child ports, in loadout order. A child produces a mount only if its subtree contains a legacy payload. Get display name from `PortDisplayName`, class and type from the installed child, and size from the first positive installed size, max size, or min size (otherwise zero). Walk the child subtree in loadout order. If descendants yield payload descriptors, use those; otherwise use the installed type if it is a legacy payload type, or the first compatible legacy payload type. Keep size duplicates; deduplicate type and class lists in first-seen order. Use `WeaponSystemAnalyzer::buildMountSummary`, `isPrimaryPayloadType`, and `isOffensivePayloadType` as the reference for legacy filtering, not the new `Payload` list. Totals and weapon rows come from `CombatStats`; turret slaveability comes from `IsPilotSlaveable` on the position. Fields without a source use the resource's null/empty defaults.

## Verification and fixtures

Schemas are illustrated in `tests/Fixtures/exports/mounting-positions/`. The populated file is a projection of the regenerated Vanguard dump with a gimbal, a loaded rack, and a manned turret. It retains the selected loadout branches and legacy rows. The empty file shows a new dump with no positions; the old-dump sample omits the field.

1. Run `php cli.php load:vehicles GAME_DATA BASELINE` from `ad899ef`.
2. Run `php cli.php load:vehicles GAME_DATA CANDIDATE` from the candidate revision against the same unpacked input.
3. Run `SC_MOUNTING_BASELINE=BASELINE/ships SC_MOUNTING_CANDIDATE=CANDIDATE/ships vendor/bin/phpunit tests/Formats/ScUnpacked/MountingPositionFleetTest.php` from the candidate checkout. It checks legacy output, position links, legacy membership, diagnostics, and the named `4.10.3-LIVE.13165946` fixtures.
4. Run the API import and v3 parity tests in the API ticket. Dump-level reconstruction does not validate the imported API response or authorize deprecation.
